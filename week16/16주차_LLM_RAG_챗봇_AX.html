영역 1 · LLM the engine

LLM — 모든 것의 엔진

언어 모델을 어떻게 부리는지가 시작입니다. 그 다음은 원리와 직접 운영으로.

배운 것
  • LLM API 호출과 프롬프트 엔지니어링
  • LCEL로 체인 구성 · 출력 파싱
  • 온도·시스템 프롬프트로 행동 제어
다음 단계
  • 프롬프트 고도화 (few-shot · 구조화 출력)
  • 파인튜닝 (LoRA/QLoRA) — 언제 필요한가
  • 로컬 LLM (Ollama) · 멀티모달
첫걸음 — "언제 파인튜닝, 언제 RAG?"를 판단할 수 있게 되는 것.
기초 다지기 · 텍스트 처리 text processing

컴퓨터가 글을 읽는 법

컴퓨터는 글자를 모릅니다. 텍스트를 잘게 쪼개고 숫자로 바꾸는 것이 모든 것의 출발점입니다.

원문"나는 밥을 먹었다"
→
토큰화tokenization
→
정제·정규화불용어 처리
→
숫자 ID모델 입력

✂️ 토큰화

문장을 토큰(단어·서브워드)으로 쪼갬. LLM은 토큰 단위로 읽고, 토큰이 곧 길이·비용의 단위.

🧹 전처리

정제·정규화·불용어 제거로 노이즈를 줄임. 좋은 입력이 좋은 결과를 만듭니다.

🇰🇷 한국어의 난관

교착어라 형태소 분석이 필요('먹었다'→먹+었+다). 띄어쓰기도 까다롭습니다.

기초 다지기 · 텍스트 표현 representation

의미를 벡터로 바꾸다

단어를 숫자로 바꾸되, 뜻이 비슷하면 값도 가깝게 — 이것이 임베딩이고, RAG 검색의 핵심 재료입니다.

1
BoW · TF-IDF
단어 빈도 기반. 단순하지만 의미·순서를 못 담음.
2
워드 임베딩 (Word2Vec)
의미를 벡터로. 가까운 뜻 = 가까운 벡터.
3
문장·문서 임베딩
문장 전체를 벡터로 → RAG 검색의 재료.
왕 − 남자 + 여자 ≈ 여왕
의미가 벡터 연산으로 드러난다
🔗 11주차 벡터 DB가 바로 이 문장 임베딩을 저장하고 검색한 것입니다.
기초 다지기 · 모델의 진화 how we reached LLMs

"다음 단어 맞히기"의 진화사

①
통계 기반 (n-gram)
앞 몇 단어로 다음을 예측. 긴 문맥을 못 봅니다.
②
RNN · LSTM
순서대로 기억하며 처리. 멀리 있는 건 잊고, 느립니다.
③
어텐션 (Attention)
"중요한 곳에 집중" — 문맥을 멀리까지 한 번에 봅니다.
④
Transformer (2017)
어텐션만으로. 병렬 처리 + 긴 문맥 → 오늘날 LLM의 기반.
핵심 전환 — Transformer가 "크게 키울수록 똑똑해지는" 길을 열었습니다.
기초 다지기 · LLM 원리 how LLMs work

LLM은 거대한 다음-토큰 예측기

방대한 텍스트로 사전학습한 Transformer가, 다음에 올 토큰을 확률로 고릅니다.

입력: "나는 밥을"

다음 토큰 확률 →
  먹었다  ████████ 0.72
  샀다     ██ 0.11
  봤다     █ 0.05

가장 그럴듯한 토큰을 이어붙인다

📚 사전학습 + 정렬

거대 데이터로 학습 후, 파인튜닝·RLHF로 대화에 맞게 다듬음.

🪟 컨텍스트 윈도우

한 번에 볼 수 있는 토큰 수의 한계. 프롬프트+대화가 여기에 들어감.

⚠️ 환각의 근원

'사실'이 아니라 '그럴듯한 다음 토큰'을 생성 → 그래서 RAG가 필요.

영역 2 · RAG grounding

RAG — 근거 있게 답하기

LLM에 내 문서를 물려, 지어내지 않고 찾아서 답하게 만드는 기술입니다.

배운 것 · 11~13주차
  • 임베딩 · 벡터 DB로 의미 검색
  • RAG 파이프라인 (검색→증강→생성)
  • 고도화 — 하이브리드 검색·리랭킹·출처 표시
다음 단계
  • 평가(RAGAS) — 정확도·환각을 숫자로
  • 고급 검색 — 쿼리 변환 · HyDE
  • GraphRAG · 멀티모달 RAG
첫걸음 — RAGAS로 내 RAG에 점수를 매기기. 측정 없이 개선은 없습니다.
영역 3 · 챗봇 설계 experience

챗봇 설계 — 쓸 만한 대화 만들기

한 번 답하고 끝이 아니라, 기억하고 · 도구를 쓰고 · 협업하는 시스템으로.

배운 것 · 14~15주차
  • LangGraph · 에이전트 루프(분기+반복)
  • 멀티턴 — 대화를 기억(Checkpointer)
  • 멀티에이전트 — 역할 분담(Supervisor)
다음 단계
  • 대화 UX · 사람 개입(human-in-the-loop)
  • 도구 확장 · MCP 연동
  • 관찰·디버깅 (LangSmith)
핵심 — 대화는 시간축(기억) + 역할축(협업)의 두 축으로 설계합니다.
영역 4 · AX AI transformation

AX — 챗봇을 넘어, 조직을 바꾸다

AX(AI Transformation)는 챗봇 하나를 만드는 일이 아니라, 업무·프로세스·조직에 AI를 이식해 일하는 방식을 근본적으로 바꾸는 일입니다.

무엇인가

흩어진 지식과 반복 업무를 AI가 흐르는 구조로 재설계. 도구 도입이 아니라 일의 재편입니다.

왜 중요한가

기업의 최대 화두. "도구를 아는 사람"보다 "도구로 조직을 바꾸는 사람"이 훨씬 귀합니다.

여러분의 위치

RAG·에이전트는 AX의 기술 재료입니다. 여러분은 이미 그 재료를 손에 쥐었습니다.

RAG·챗봇이 '무엇을 만들 수 있나'라면, AX는 '그래서 무엇을 바꾸나'입니다.

실무에서 조심할 것 common myths

이렇게 착각하기 쉽습니다

01 "LLM은 다 안다"
모르는 건 그럴듯하게 지어냅니다(환각). 그래서 RAG로 근거를 대야 합니다.
02 "RAG를 쓰면 환각이 없다"
검색이 틀리면 답도 틀립니다. 평가와 출처 표시가 함께 가야 합니다.
03 "복잡한 에이전트가 좋다"
복잡할수록 느리고 예측이 어렵습니다. 단순한 것부터, 필요할 때만 에이전트.
04 "파인튜닝이 정답이다"
대부분 RAG·프롬프트로 충분합니다. 파인튜닝은 근거를 갖춘 최후의 선택.
05 "데모가 곧 완성이다"
배포·평가·안전(가드레일)까지 가야 진짜 프로덕션입니다.
