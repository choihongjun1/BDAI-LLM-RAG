판단 · 4문항

내 프로젝트, 몇 개나 해당되나

해당되는 항목에 체크
  • 다음 단계가 실행 중에 달라지는가 — 상황에 따라 검색을 할 수도, 계산기를 쓸 수도, 그냥 답할 수도 있다
  • 같은 일을 조건이 될 때까지 되풀이하는가 — 결과가 부족하면 다시 검색해서 보강해야 한다
  • 여러 단계가 데이터를 공유하고 누적하는가 — 앞 단계 결과를 뒤에서 계속 참조한다
  • 대화를 세션별로 이어야 하는가 — 사용자별로 이전 대화를 기억해야 한다

처음부터 LangGraph

나중에 옮기면 구조를 다시 짜야 합니다. 시작할 때 그래프로 잡으세요.

기존 체인은 버리지 않습니다. 노드 함수 안에서 chain.invoke(...)를 호출하면 그대로 살아납니다. 노드는 그냥 파이썬 함수이기 때문입니다.

비교 · 무엇이 안 되는가

LCEL은 한 방향으로만 흐른다

LCEL(|)이 만드는 흐름은 근본적으로 순환 없는 그래프(DAG)입니다. 그래서 다음이 안 되거나, 억지로 하면 코드가 무너집니다.

핵심 · 순환

가장 큰 차이는 되돌아오는 화살표 하나

에이전트의 본질

답이 나올 때까지 되풀이한다

생각 → 행동 → 관찰 → 다시 생각. 몇 바퀴 돌지는 실행해 봐야 압니다. 코드를 짤 때 정할 수 없는 값이죠. DAG는 이 되돌아오는 화살표 자체가 불가능하므로, 에이전트를 표현할 수 없습니다.

그래서 “LangGraph를 왜 쓰나요”의 답은 한 단어로 순환입니다. 조건 분기와 상태는 그 순환을 쓸모 있게 만드는 부품입니다.

자주 나오는 질문

“그냥 while문으로 짜면 되지 않나요?”

됩니다. 프로토타입이라면 오히려 그게 빠를 수도 있습니다. 다만 프로젝트가 커지면 아래를 전부 직접 만들게 됩니다.

직접 만들어야 하는 것 ①

상태 관리

대화와 도구 결과를 어디에 어떻게 쌓을지, 덮어쓸지 이어붙일지 매번 정해야 합니다.

② ③

대화 저장 · 스트리밍

세션별 기억(체크포인터)과 토큰 단위 출력. 둘 다 직접 만들면 꽤 큰 작업입니다.

④ ⑤

중단·재개 · 사람 개입

중간에 멈췄다 이어가기, 위험한 도구 실행 전 승인받기.

더 큰 문제는 가시성입니다. while문으로 짜면 흐름이 코드 속에 숨습니다. 어디서 잘못됐는지 찾으려면 코드를 처음부터 읽어야 합니다.
LangGraph는 흐름이 노드와 엣지로 보입니다. draw_mermaid() 한 줄이면 그림이 나오고, 그 그림이 곧 발표 자료이자 디버깅 지도가 됩니다.

역할 · 분담

LLM은 판단, LangGraph는 실행과 흐름

역할담당하는 일
LLM
두뇌		 판단
무엇을 할지		 도구를 쓸까? 어떤 도구에 어떤 값을 넣을까? 이제 답해도 될까?
LangGraph
신경계 · 골격		 실행 · 흐름
어떻게 돌릴지		 도구를 실제로 실행하고, 결과를 다시 LLM에게 전달하고, 분기·반복·상태·기억을 관리하고, 언제 멈출지 통제한다
LLM은 “무엇을 할지” 결정만 합니다. 그 결정을 실제 동작으로 옮기는 것은 전부 LangGraph 쪽 일입니다. 이 경계를 헷갈리면 프롬프트로 해결할 문제와 그래프로 해결할 문제가 뒤섞입니다.
디버깅에 바로 쓰입니다. 도구를 엉뚱하게 골랐다 → LLM(프롬프트·도구 설명) 문제. 도구는 맞는데 결과가 반영이 안 된다 → 그래프(상태·엣지) 문제.

뼈대 · 에이전트 루프

노드 두 개와 분기 하나가 전부다

이 그림이 15주차 전부입니다. 나머지는 여기에 도구를 늘리고, 메모리와 안전장치를 얹는 일입니다.
agent_skeleton.py
from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    messages: Annotated[list, add_messages]   # 쌓인다

def chatbot(state: State):                    # 판단
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
builder.add_node("tools", ToolNode(tools))    # 실행

builder.add_edge(START, "chatbot")
builder.add_conditional_edges("chatbot", tools_condition)
builder.add_edge("tools", "chatbot")          # ← 순환

graph = builder.compile(checkpointer=MemorySaver())

config = {"configurable": {"thread_id": "user-123"}}
graph.invoke({"messages": [("user", "...")]}, config)

역할 · 구체화

그래서 LangGraph가 해주는 다섯 가지

① 루프의 뼈대

생각 → 행동 → 관찰 → 반복

chatbot ↔ tools를 조건 분기로 이은 순환 구조. 에이전트의 심장입니다.

② 자율적 라우팅

스스로 경로를 고른다

tools_condition이 “도구를 요청했으면 tools로, 아니면 종료”를 판정합니다. 에이전트의 자율성이 여기서 나옵니다.

③ 상태로 맥락 유지

매 스텝 전체를 보고 판단

messages에 대화와 도구 결과가 add_messages로 쌓여, LLM이 항상 전체 맥락 위에서 결정합니다.

④ 멀티턴 메모리

세션별로 기억한다

checkpointer + thread_id. 사용자마다 대화가 따로 이어집니다.

⑤ 안전장치와 제어

자율성을 통제 가능하게

재귀 한도(무한 루프 방지), 사람 승인(human-in-the-loop), 중단과 재개.

실행 가능하고 통제된 흐름으로

LLM이 두뇌라면 LangGraph는 그 판단을 몸으로 옮기는 신경계이자 골격입니다.

거의 이 다섯 가지에서 막힌다

증상원인해결
무한 루프 · 재귀 한도 초과종료 조건이 없거나 라우터가 항상 계속을 반환종료 경로를 먼저 만들고 테스트 · 루프 횟수 필드 추가
LLM이 직전 대화를 모른다messages에 리듀서를 안 붙여 덮어쓰기 중Annotated[list, add_messages]
멀티턴이 안 된다checkpointer만 붙이고 thread_id를 안 넘김invoke 호출마다 config 전달
엉뚱한 노드로 간다라우터 반환값과 분기 지도의 이름표 불일치문자열을 상수로 빼서 오타 차단
도구를 안 쓰거나 잘못 고른다도구 설명(docstring)과 타입 힌트가 부실그래프가 아니라 도구 정의를 고칠 것
마지막 줄이 중요합니다. 증상은 그래프에서 보이지만 원인이 LLM 쪽인 경우가 많습니다. 7장의 역할 분담표로 어느 쪽 문제인지 먼저 가르세요.
